# Supply 前台收件

由一级管理员 `tjt740` 登录「系统设置 → Supply 邮件服务」，输入 Supply 后台签发的原始 Token，点击「验证并保存 Token」。服务端调用 `/supply/require` 校验成功后保存；失败保留原值。未配置时继续使用现有邮箱收件器；配置成功后前台按邮箱自动选择：邮局后台已录入的邮箱优先使用现有收件器，未录入的邮箱才查询 Supply，不需要重启。匹配邮箱地址或登录用户名时忽略大小写；本地取件失败不会改查 Supply。后台邮箱管理、轮询及卡密链接继续使用现有收件流程。

`/api/public-mail-config` 在配置 Supply 后返回 `provider: auto`，前台保留本地邮箱的垃圾箱入口。Supply 邮箱仍只支持收件箱，其错误标注为 `(Supply)`；只有响应明确提供连接方式时才显示“直连”或“代理”。

在「展示邮件数量」中保存 1–20 的整数（默认 5），前台每个邮箱按该数量展示最近邮件，无需分页；不足设定数量时显示实际返回数量。批量查询会连续展示各邮箱的结果。设置修改后，前台下次查询读取最新数量；前台请求无法覆盖管理员保存的数量。Supply 只提供收件箱查询，因此启用后隐藏垃圾箱入口。现有前台密钥开关及个人密钥的邮箱授权范围仍由服务端校验。

## 接口与凭证

- `GET /admin/api/supply-token`：返回是否已配置、已保存的展示数量及最近连通性检测结果，不返回 Token 或其摘要。
- `POST /admin/api/supply-token` 的 `action: reveal`：仅 `tjt740` 点击眼睛图标时返回已保存 Token；请求需通过同源、持久化身份及当前会话校验，不调用上游或修改连通状态。
- `POST /admin/api/supply-token`：接受 JSON `{ "token": "<SUPPLY_TOKEN>" }`，校验 16–512 个可见 ASCII 字符及同源请求；上游验证成功才保存。
- 同一路径的 POST 还支持 `action: settings` 保存 `email_limit`、`action: test` 检测已保存 Token，以及 `action: preview` 根据 `email` 和 `email_limit` 预览邮件。预览不会保存输入数量，也不会计入取件日志或卡密使用次数。
- 检测结果显示连通状态、检测时间、响应耗时和检测阶段。Token 校验只验证账号接口；邮箱预览成功才验证完整收件链路。结果与当时检测的 Token 关联，更新 Token 后不会沿用旧凭证的结果。
- 连接示意图中间按钮与「测试连通」共用真实检测请求，支持点击和键盘操作，检测期间禁止重复提交。等待时显示发出信号、节点脉冲和扫描环；成功后显示回程信号与扩散波纹，失败后短暂反馈并停留在断线状态，点击中心可重试。动画不会自动重试请求；离屏或页面隐藏时暂停，减少动态效果模式保留静态状态。
- 配置接口与配置界面仅持久化身份为 `tjt740` 的一级管理员可访问，普通管理员即使获得系统设置权限也不可访问。输入框默认隐藏；眼睛图标可显示当前输入的 Token，输入框为空时按需读取已保存 Token。再次点击或离开设置栏目时清除已读取的值，未保存的新输入恢复遮盖；提交结束后清空，不使用浏览器存储。
- Token 默认存入 `db/supply/token.json`，目录权限 `0700`、文件权限 `0600`，通过临时文件原子替换。该目录已加入 `.gitignore`。Docker 原有 `/app/db` 挂载包含此目录；如通过 `SUPPLY_TOKEN_FILE` 指定其他路径，需自行保证该路径持久化。
- GitHub Actions 发布时保留服务器上的 `db/supply/`，不会覆盖或删除已保存的 Token。本地 Token 不随代码上传，首次上线需在服务器后台配置。
- 每次收件读取一次 Token，同次查询使用固定凭证；损坏配置不会静默回退。Token 失效需重新登录 Supply 获取新值，再从设置页更新。
- 邮件与 Token 接口均设置 `Cache-Control: no-store, private`；不会记录或透传上游错误正文。

## Supply 数据处理

服务端依次请求 `/supply/require` 和 `/supply/getMail`，前端不直接携带 Supply Token。邮箱必须完整精确匹配；精确查询未命中时最多扫描 5 页、每页 200 个账号。兼容数组、`data.list`、`data.rows`，正确保留字符串或数字账号 ID。

本地 SQLite 为忽略大小写的邮箱地址和用户名查询建立索引，前台路由和收件器均使用这些索引。Supply 精确匹配成功的账号 ID 在进程内缓存 60 秒，按 Token 摘要与邮箱隔离，最多保留 512 条；更新 Token 后重新查询，失败及未找到的邮箱不缓存，取件错误会清除对应 ID。每次仍请求上游获取最新邮件，不缓存邮件内容；新增到邮局的邮箱立即优先走本地查询。

邮件按归一化后的 UTC 时间倒序截取设定数量，保留 HTML 原始正文及图片引用，在隔离的邮件阅读框内渲染；纯文本保留换行。阅读时正文按实际内容和图片高度展开，邮件正文与主题不参与界面翻译。明确属于其他收件人的邮件会被排除，缺少收件人字段时保留。`getMail` 的 `1005` 与空数据返回空列表；认证、限流、超时、网络及格式错误分别处理。上游最多返回多少封由 Supply 决定，不能将返回结果视为邮箱全部历史邮件；请求超过 10 封时通过上游 `number` 参数请求更多邮件，但返回数量仍由 Supply 决定。

## 验证

- `.venv/bin/python -m unittest discover -s tests -p test_supply_mail.py`：模拟上游响应，验证匹配、扫描边界、排序、正文处理、凭证持久化及访问控制。
- `node --test tests/test_i18n_motion.cjs`：繁体中文、动态文案及语言切换。
- 安装 Playwright 后运行 `node --test tests/browser/public_mail_key.cjs`：配置界面、五封邮件、批量查询、手机布局及邮件原文保护；支持 `PLAYWRIGHT_MODULE`、`BROWSER_CHANNEL=chrome`。

自动化测试使用隔离数据库和模拟上游。真实接入还需 `tjt740` 配置有效 Token，并用该 Supply 账号有权访问的邮箱完成一次收件验证。
